`Input` is the low-level single-line text-entry component. It owns native input behavior and Augur styling, but not validation rules, form state, or submission policy.

Use [FormField](/patterns/form-field) when the label, description, error message, and required wiring should be composed as one reusable field pattern.

## When to use

- Short single-line values such as names, identifiers, dates, emails, and URLs.
- A one-off field with a real `<label>` association.
- Inside FormField when the field needs helper text, error messaging, or repeated accessibility wiring.
- With the native `type` that matches the value's shape where possible.

## When not to use

- Do not use Input for choosing among known alternatives; use a selection control.
- Do not use it for multi-line prose; use a textarea component when available.
- Do not use read-only Input as a general display component outside a form context.
- Do not move validation logic into Input; consumers own validation policy.

## Sizes

Input uses the standard `md` control band: 36px structural height, 12px horizontal padding, and 0px control radius. It is full width by default so the surrounding composition owns field width.

On coarse pointers, the actionable target expands to at least 44px high and wide.

## States

- **Default:** transparent field with a 1px semantic input edge (`--input`, Mist in both themes).
- **Hover:** the edge strengthens to `--input-hover` (Graphite in light, Pewter in dark). Hover does not apply to disabled, read-only, or invalid fields.
- **Focus:** shared 2px `:focus-visible` ring with a 2px offset from `--ring`.
- **Disabled:** native `disabled`, non-interactive, reduced opacity, `cursor: not-allowed`.
- **Invalid:** `aria-invalid="true"` plus the semantic destructive edge; visible error copy carries the meaning.
- **Read-only:** native `readOnly`; value remains focusable, selectable, and copyable on the quiet `--muted` surface.

## Accessibility

- Associate a real visible label with `htmlFor`/`id`; placeholder text is not a label.
- Connect descriptions and errors through `aria-describedby`.
- Use `aria-invalid` only while the field is invalid and keep a visible message that explains the problem.
- Keep disabled and read-only distinct: disabled removes interaction; read-only preserves focus and copy.
- Use native `required` where the field is required.
- Shared focus and pointer-target behavior comes from the system interaction contract.

## API

```tsx
import { Input } from "@augurproject/design-system";
```

| Prop | Type | Default | Description |
| --- | --- | --- | --- |
| `invalid` | `boolean` | `false` | Adds `aria-invalid` and the semantic invalid edge |
| `disabled` | `boolean` | `false` | Native disabled state |
| `readOnly` | `boolean` | `false` | Native read-only state |
| `required` | `boolean` | `false` | Native required state |
| `type` | native input types | `"text"` | Value shape |
| `className` | `string` | — | Extends the component classes |
| `ref` | `React.Ref` | — | Ref for the underlying input |
| …props | native input attributes | — | Passed through to the native element |

### Controlled and uncontrolled usage

```tsx
<Input name="queryName" defaultValue="Q3 records review" />

const [value, setValue] = useState("");
<Input
  value={value}
  onChange={(event) => setValue(event.currentTarget.value)}
  invalid={value.length === 0}
/>
```

### Validation ownership

Input carries no validation rules. Compute validity in the product layer and express the result through `invalid` plus visible error copy, either with FormField or hand-wired `aria-describedby`.

## Design rationale

Input remains a thin native component so it can participate in different form compositions without taking ownership of product policy. Semantic roles and shared geometry keep it consistent with Button and other controls without coupling it to a form framework.

## Related components and patterns

Use [FormField](/patterns/form-field) for repeated field wiring. Use [Button](/components/button) for form commands. A future selection component should own known-option choice semantics rather than overloading Input.

## Verification

Repository tests cover keyboard entry, labeling, described-by wiring, invalid/disabled/read-only behavior, theme roles, square radius, coarse-pointer sizing, and axe findings.
