## When to use

- At the top of a page or full-page panel that needs a clear title and optional supporting line.
- When wayfinding belongs with the title through breadcrumbs or a quiet back action.
- When page-level operations should sit beside the title without becoming a separate toolbar.
- When there is one clear primary action and supporting actions need a consistent place.

<DocExample example={examples.patterns.composition} />

## When not to use

- Do not use PageHeader inside Cards or compact record panels.
- Do not use it as a generic mid-page grouping header.
- Do not put form submission policy into the header when the action belongs to a specific form region.
- Do not present multiple primary actions with equal emphasis.

## Anatomy

| Part | Responsibility |
| --- | --- |
| `PageHeader` | Page-title region |
| `PageHeaderBreadcrumb` | Named wayfinding navigation |
| `PageHeaderContent` | Title/description and action layout |
| `PageHeaderTitle` | Page heading |
| `PageHeaderDescription` | Supporting explanation |
| `PageHeaderActions` | Page-level action row |

## Behavior and adaptive layout

Long titles and descriptions wrap inside the title column. Actions stay aligned to the title region on wider layouts and move below the title content at narrow widths.

The pattern changes layout without changing DOM priority: primary content remains first and the first primary action remains first among actions.

## Accessibility

- `PageHeader` renders a real `header` region.
- `PageHeaderTitle` renders `h1` by default; use `headingLevel` when the pattern is intentionally nested below page level.
- Breadcrumbs use a named `nav`; consumers provide the list and link markup.
- A simple back Button does not need a nav landmark if it is a single command-like affordance.
- Action order in the DOM should match visual priority.

## API

```tsx
import {
  PageHeader,
  PageHeaderBreadcrumb,
  PageHeaderContent,
  PageHeaderTitle,
  PageHeaderDescription,
  PageHeaderActions,
} from "@augurproject/design-system";
```

`PageHeaderTitle` accepts `headingLevel` from 1–6. Every part accepts native attributes for its element, `className`, and a React 19 ref prop.

## Related components and patterns

Use [Button](/components/button) for page actions. Use [Card](/components/card) for local grouped regions below the header. For a page with no actions, keep the same header structure rather than inventing a different title treatment.

## Verification

Repository tests cover heading semantics, breadcrumb naming, action composition, long-content wrapping, theme behavior, responsive reflow, and axe findings.

## Design rationale

The pattern owns structure; consumers own the words, links, and commands. The page hierarchy remains visible through typography, spacing, and alignment rather than a container or decorative hero treatment. PageHeader supplies one stable place for page-level responsibility without introducing product-specific workflow.
