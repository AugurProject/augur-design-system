Every component in `@augurproject/design-system` follows the same ownership model: Augur owns the API, styling, documentation, and verification contract even when a familiar implementation shape comes from shadcn or a primitive library.

## Layering

Components consume semantic roles and shared foundations. They do not own system-wide color, focus, motion, spacing, or geometry rules unless a component has a concrete exception.

```text
Foundations → Tokens → Primitives → Components → Patterns → Products
```

Use native elements first. Introduce a primitive such as Radix when the interaction model requires behavior native elements do not provide cleanly.

## Visual contract

Component CSS uses semantic role custom properties rather than raw color values or generated color primitives directly.

Shared decisions live in:

- [Layout and geometry](/foundations/layout-geometry)
- [Interaction](/foundations/interaction)
- [Color system](/foundations/color)
- [Theming](/foundations/theming)
- [Fonts and typography](/foundations/fonts)

A component page explains how those rules apply and documents exceptions; it should not restate a second foundation system.

## API conventions

- Public exports use PascalCase and are re-exported from the package root.
- Internal file organization is not public API.
- Prefer small string-union variant/size props over open-ended visual props.
- Composition parts use real semantic elements where possible.
- React 19 refs pass directly; avoid `forwardRef` without a compatibility requirement.
- `className` extends the component rather than replacing its contract.
- Product workflow, validation policy, and domain state stay outside the design-system component.

## Documentation contract

Every component page must help a consumer make a correct decision, not merely enumerate props.

The current build-time required sections are:

```text
When to use
When not to use
Variants
Sizes
States
Accessibility
API
Design rationale
```

Use `not applicable` honestly rather than inventing speculative variants or states to fill the outline.

Where they add decision value, also document:

```text
Anatomy
Adaptive behavior
Related components / patterns
Verification
```

Live examples must import the real package component. Displayed code should come from the same example source so rendering and sample text cannot drift independently.

## Testing expectations

A component change should prove the parts relevant to its contract:

- package/unit tests for exports and API behavior;
- interaction/accessibility tests for keyboard, state, semantics, and axe findings;
- docs/browser fixtures for rendered geometry and theme behavior when visuals change;
- source-registry generation/consumer checks when distribution changes;
- maintainer visual review where the current acceptance gate applies.

Passing deterministic tests does not establish visual acceptance.

## Registry distribution

The source registry is generated from canonical repository sources. Registry output must not become a hand-maintained second implementation.

The base `augur-theme` item carries the shared system contract; component and pattern items compose on top of it. Consumers should pin verified refs for reproducibility.

## Adding or changing a component

1. Confirm the component belongs in Components rather than Patterns or a product surface.
2. Reuse maintained foundations instead of inventing local visual rules.
3. Define the smallest API that serves the concrete use case.
4. Implement with native semantics or an appropriate primitive.
5. Document selection, behavior, accessibility, and API.
6. Add real examples and relevant deterministic/browser verification.
7. Verify registry output if the component is externally consumable.
8. Escalate unresolved system decisions instead of silently creating a local exception.
